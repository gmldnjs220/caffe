# 혼자서 DB를 설계할 때의 과정

이번 원보틀 DB를 만든 순서 그대로 정리했습니다. 다음에 혼자 할 때 이 순서대로 따라가면 됩니다.

---

## 1단계. 기능을 문장으로 적는다

코드나 표부터 그리지 말고, **"누가 무엇을 한다"** 문장으로 먼저 씁니다.

- 손님은 회원가입하고 로그인한다.
- 손님은 메뉴를 보고, 온도와 옵션을 골라 주문한다.
- 비회원도 전화번호만 넣으면 주문할 수 있다.
- 손님은 먹어 본 메뉴에 별점과 후기를 남긴다.
- 사이트는 손님 취향, 인기, 평점, 직원 추천으로 메뉴를 추천한다.
- 관리자는 메뉴와 주문, 직원 추천 메뉴를 관리한다.

> 팁: 이번에 "비회원 주문", "주문번호 001~100", "전화번호 필수" 같은 규칙이 설계 도중에 나왔죠. 이런 건 **처음 문장 쓸 때** 최대한 끌어내 두면 나중에 고칠 게 줄어듭니다. "주문할 때 손님은 무엇을 입력하지?", "번호는 어떻게 불러주지?"처럼 실제 매장 상황을 상상하면서 질문해 보세요.

## 2단계. 명사를 뽑아서 테이블 후보로 만든다

1단계 문장에서 **명사**에 밑줄을 그으면 그게 테이블 후보입니다.

손님(users), 메뉴(menus), 주문(orders), 후기(reviews), 옵션(menu_options), 태그(tags) …

그리고 각 명사가 **어떤 정보를 가지는지** 적으면 그게 컬럼입니다.
- 메뉴 → 이름, 설명, 가격, 온도, 카페인 여부 …
- 주문 → 주문번호, 전화번호, 상태, 총액, 주문 시간 …

## 3단계. 이미 있는 데이터를 확인한다

새로 만들기 전에 **이미 가진 데이터**를 봅니다. 이번엔 `js/menu-data.js`였습니다.

여기서 발견한 것들이 설계에 그대로 반영됐습니다.
- 그룹 → 카테고리 → 메뉴 **3단 구조** → 테이블 3개
- `price: 4.5`(천 원 단위 소수) → DB에서는 **4500 정수**로 (돈은 소수로 저장하면 계산 오차가 생김)
- 어린이 음료처럼 **가격이 여러 개**인 메뉴 → `menu_variants` 테이블을 따로
- `temp`가 "없음"과 `null`로 뜻이 다름 → DB에서 `NULL`과 `'none'`으로 구분

> 팁: 데이터 안에 **예외**(가격이 2개인 메뉴, 온도 표시가 없는 메뉴)가 있는지 꼭 찾아보세요. 설계가 틀어지는 건 대부분 예외 때문입니다.

## 4단계. 관계를 정한다 (1:N인지 N:M인지)

두 테이블씩 짝지어서 질문합니다.

| 질문 | 답 | 결과 |
|---|---|---|
| 카테고리 하나에 메뉴가 여러 개? 메뉴 하나는 카테고리 하나? | 예 / 예 | **1:N** → 메뉴에 `category_id` |
| 주문 하나에 메뉴 여러 개? 메뉴 하나가 여러 주문에? | 예 / 예 | **N:M** → 중간 테이블 `order_items` |
| 메뉴 하나에 태그 여러 개? 태그 하나가 여러 메뉴에? | 예 / 예 | **N:M** → 중간 테이블 `menu_tags` |
| 주문 하나에 결제 하나? | 예 | **1:1** → `payments.order_id` UNIQUE |

규칙은 간단합니다.
- **1:N** → "N쪽" 테이블에 상대 id(FK)를 넣는다.
- **N:M** → 가운데에 연결 테이블을 하나 만든다.

## 5단계. 함정 체크리스트

이번 설계에서 일부러 챙긴 것들입니다. 혼자 할 때 이 목록으로 한 번 훑어보세요.

- [ ] **돈은 정수(원 단위)로** 저장했나?
- [ ] **나중에 바뀌는 값을 복사해 뒀나?** 메뉴 가격이 오르면 옛날 주문 금액도 바뀌면 안 됨 → `order_items`에 이름·가격 복사본
- [ ] **비워도 되는 칸(NULL)과 꼭 필요한 칸(NOT NULL)** 을 구분했나? (비회원 주문 → `user_id`는 NULL 허용, `contact_phone`은 필수)
- [ ] **겹치면 안 되는 값에 UNIQUE**를 걸었나? (이메일, 주문당 후기 1개)
- [ ] **값의 범위를 CHECK로 막았나?** (별점 1~5, 수량 1 이상, 주문번호 1~100)
- [ ] **삭제할 때 어떻게 되는지** 정했나? 후기 삭제 → 후기 사진도 삭제(CASCADE), 회원 탈퇴 → 주문 기록은 남김(`deleted_at`)
- [ ] **비밀번호를 원문으로 저장하지 않았나?** (해시만 저장)
- [ ] **자주 검색하는 컬럼에 인덱스**를 걸었나? (전화번호로 주문 조회 등)

## 7단계. SQL로 옮기고 직접 실행해 본다

설계는 **실행해 봐야 끝**입니다. 이번에도 실제로 돌려서 확인했습니다.

1. `CREATE TABLE`을 순서대로 작성 (**참조당하는 테이블 먼저**: users → menus → orders → order_items …)
2. 기존 데이터를 넣는 SQL 작성 (이번엔 `db/make-seed.js`로 menu-data.js에서 자동 생성)
3. 실제로 실행하고, 일부러 틀린 데이터를 넣어 봐서 막히는지 확인
   - 예: 같은 주문번호를 두 번 넣기 → 에러가 나야 정상

실행해 보는 방법:
- **Supabase** (추천): supabase.com 가입 → 새 프로젝트 → 왼쪽 **SQL Editor** → `db/schema.sql` 내용 붙여넣고 Run → 이어서 `db/seed.sql` Run → **Table Editor**에서 확인
- **내 컴퓨터**: PostgreSQL 설치 후 `psql -d 데이터베이스이름 -f db/schema.sql`, 그다음 `-f db/seed.sql`

## 8단계. 기능 하나씩 시나리오로 검증한다

마지막으로 "이 기능을 할 때 어떤 테이블을 읽고 쓰지?"를 따라가 봅니다.

- **비회원 주문**: 장바구니(브라우저) → `orders`(user_id 없이, 전화번호·주문번호) → `order_items` → `order_item_options` → 화면에 "주문번호 047"
- **후기 쓰기**: 로그인 → 내 주문의 `order_items` 하나 선택 → `reviews` (주문 한 줄당 1개)
- **직원 추천**: 관리자가 `staff_picks`에 등록 → 메뉴 추천 화면에서 노출 중인 것만 조회

여기서 막히는 곳이 있으면 테이블이나 컬럼이 빠진 겁니다. 2단계로 돌아가서 고치면 됩니다.
